# RFC: предупреждение с отсроченной мерой

Статус: предложение для обсуждения.

## Зачем

Сейчас оператор может предупредить пользователя, сразу заблокировать его,
ограничить скорость или оставить решение человеку. Для сценариев с высоким
риском ложного срабатывания не хватает долговечной цепочки:

1. предупредить пользователя;
2. дать ему настраиваемое время на реакцию;
3. повторно проверить актуальность нарушения;
4. применить выбранную меру или отправить кейс оператору.

Обычная пауза внутри процесса для этого не подходит: состояние должно
переживать перезапуск backend, повторную доставку событий и временную
недоступность внешнего сервиса.

## Предлагаемая модель

Отдельная таблица `violation_enforcement_cases` хранит один кейс на нарушение и
политику. Минимальные состояния:

```text
pending_notice -> grace_period -> due -> enforced
                      |           |       |
                      |           |       +-> failed / manual_review
                      |           +-> cancelled / resolved
                      +-> paused_for_support
```

Кейс хранит `violation_id`, `user_uuid`, состояние, снимок политики,
`deadline_at`, число попыток, результат доставки, причину паузы/отмены и
временные метки. Уникальный ключ по нарушению и политике делает постановку в
очередь идемпотентной.

Планировщик выбирает просроченные кейсы через `FOR UPDATE SKIP LOCKED`. Перед
мерой он обязательно проверяет, что:

- нарушение существует и не аннулировано;
- пользователь не находится в whitelist;
- мера ещё не применена;
- кейс не приостановлен поддержкой;
- пользователь и связанный объект панели всё ещё доступны.

Платёжная история не является частью этой RFC. При необходимости дополнительные
условия можно добавить позже как расширяемые resolvers, не связывая ядро с
конкретной биллинговой системой.

## Настройки политики

Настройки добавляются через `shared/config_service.py`, чтобы автоматически
появиться в существующем UI:

- включено ли отложенное применение мер;
- виды нарушений и минимальный скор;
- длительность ожидания, по умолчанию 12 часов;
- действие после дедлайна: `manual_review`, `disable`, `throttle`, `none`;
- скорость и срок ограничения для `throttle`;
- что делать при ошибке доставки предупреждения;
- максимальное число повторов и интервал между ними;
- приостанавливать ли дедлайн после обращения в поддержку;
- пилотный режим и список тестовых UUID.

Безопасное значение по умолчанию для существующих установок — функция
выключена, финальное действие — `manual_review`.

## Обращение в поддержку

Пауза поддержки опциональна. Событие `customer_contacted` переводит активный
кейс в `paused_for_support`; автоматическая мера больше не выполняется, пока
оператор явно не возобновит, не отменит или не применит её вручную.

Источники события:

1. встроенные тикеты Remnawave Admin;
2. тикеты Bedolaga, если интеграция включена;
3. универсальный входящий endpoint для любого support-бота или helpdesk.

Предлагаемый универсальный контракт:

```http
POST /api/v3/enforcement/support-events
Authorization: Bearer <scoped-api-key>
Idempotency-Key: <provider-event-id>
Content-Type: application/json

{
  "event": "customer_contacted",
  "user": {
    "uuid": "00000000-0000-0000-0000-000000000000"
  },
  "ticket": {
    "provider": "generic-helpdesk",
    "external_id": "ticket-123",
    "url": "https://support.example.com/tickets/123"
  },
  "occurred_at": "2026-01-01T12:00:00Z"
}
```

Идентификация допускает `uuid`, `telegram_id` или `email`, но событие
принимается только при одном однозначном совпадении. Endpoint использует
отдельное право API-ключа, ограничение частоты, идемпотентность и аудит. Текст
обращения передавать не нужно: достаточно факта и ссылки на тикет.

## Пилотный режим

Пилот нужен для проверки на реальных данных без создания множества аккаунтов и
без риска массовой блокировки.

- `dry_run`: строит кейс, дедлайн и решение, но не отправляет сообщение и не
  меняет пользователя;
- `deliver_only`: отправляет предупреждение, но финальную меру только
  протоколирует;
- `selected_users`: выполняет цепочку только для явно перечисленных UUID;
- кнопка «Смоделировать» показывает выбранный шаблон, срок, условия отмены и
  итоговое действие;
- кнопки «Выполнить шаг сейчас» доступны только администраторам с правом
  разрешения нарушений и оставляют запись в аудите.

Пилотный режим не должен ослаблять whitelist, RBAC или проверку области
видимости администратора.

## UI

В разделе «Нарушения» предлагается отдельная вкладка «Применение мер», а не
добавление настроек в «Обнаружение нарушений». На ней находятся:

- явный главный переключатель;
- редактор политики и финального действия;
- очередь с состоянием и оставшимся временем;
- фильтры `grace_period`, `paused_for_support`, `manual_review`, `failed`;
- действия «пауза», «возобновить», «отменить», «применить сейчас»;
- пилот и симуляция.

## Разбиение реализации

1. Миграция, репозиторий кейсов, планировщик и unit-тесты переходов.
2. Настройки политики, API и UI очереди.
3. Адаптер встроенных тикетов и универсальный support endpoint.
4. Пилот, симуляция и интеграционные тесты восстановления после рестарта.

Каждый шаг должен быть пригоден к отдельному ревью. Полная совместимость с
внешней Ban System Bedolaga не требуется: она нужна только если Remnawave Admin
должен стать backend для всего её UI, статистики, наказаний и настроек. Для этой
цепочки достаточно публичных API уведомлений и support-events.

## Критерии приёмки

- кейс восстанавливается после рестарта без потери дедлайна;
- одно событие не создаёт две меры;
- перед мерой всегда выполняется повторная проверка;
- обращение в поддержку атомарно останавливает автоматическое решение;
- сбой уведомления и сбой меры различаются в журнале;
- `manual_review` ничего не меняет в Remnawave;
- пилот не может затронуть пользователя вне списка;
- покрыты гонки «обращение одновременно с дедлайном» и «ручное решение
  одновременно с планировщиком».
