# Обновление

```bash
cd /путь/к/remnawave-admin
docker compose pull
docker compose up -d
```

Структура базы приводится в порядок сама при первом запуске: миграции применяются на старте. Панель, коллектор и бот стартуют одновременно, но мигрирует кто-то один — остальные ждут своей очереди и получают уже готовую схему.

## Какой образ приезжает

| Ветка репозитория | Тег образа | Кому |
|-------------------|-----------|------|
| `main` | `latest` | всем |
| `dev` | `dev` | тем, кто готов ловить сырое |

По умолчанию compose тянет `latest`. Переключиться на `dev` можно, поменяв тег образа в `docker-compose.yml`, но там живут изменения, которые ещё никто не проверял в бою.

## Агент на нодах

Агент обновляется отдельно и своим темпом — панель работает и со старым. Но новые возможности нод (например, [детект торрентов через nDPI](/guide/torrents)) появляются только вместе со свежим агентом.

На каждой ноде:

```bash
cd /opt/remnawave-node-agent
docker compose pull
docker compose up -d
```

Версия агента видна в панели на карточке ноды. Если она отстаёт от требуемой, панель об этом скажет.

## Перед крупным обновлением

- Прочитайте [заметки к релизу](https://github.com/Case211/remnawave-admin/releases) — раздел «Важно» там как раз про то, что придётся сделать руками
- Сделайте [бэкап базы](/guide/backups) — панель умеет снимать его сама, из интерфейса
- Держите под рукой предыдущий тег образа: откат — это подмена тега и `docker compose up -d`

::: warning Откат после миграций
Миграции меняют схему базы вперёд. Откат образа на версию назад после применённых миграций может не завестись — поэтому бэкап перед обновлением важнее, чем кажется.
:::

## Проверка после обновления

```bash
docker compose ps
docker compose logs --tail 100 web-backend
```

Текущая версия панели и наличие свежей показываются карточкой на дашборде.
